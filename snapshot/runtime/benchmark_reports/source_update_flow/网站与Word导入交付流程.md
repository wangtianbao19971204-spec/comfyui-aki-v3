# 网站与 Word 导入、分类、发布和交付流程

最新实战批次：[渡鸦 816 条增量导入与交付](../2026-09-28_raven_increment/渡鸦增量导入与交付.md)。旧版只读演练保留在文末，作为版本漂移门禁的历史证据。

本入口适用于一次完整资料更新。每批使用独立目录，保留原件、网页固定版本、逐项处置、暂存、备份和收据。`flow_gate.py` 是只读检查器；旧批次脚本中含固定路径、计数和进程号，不能复制后直接对新批次执行。

## 1. 固定输入

1. 保存网站 `data-source.json`、`current.json`、`manifest.json`、`codexes.json` 和全部实际读取的数据集。记录 release ID、每份文件的 SHA-256、实读条数和带图条数。外部 `dataUrl` 要保存其实际返回字节及哈希；回退到网站发布版须明确记为回退，不能把目录标称数当实读数。
2. 保存 Word 原件路径和 SHA-256；解析结果、段落信息与原件哈希同批归档。旧资料被上游撤下不自动删除本地内容。
3. 完成采集和解析后创建不可覆盖的批次清单：

   ```powershell
   python benchmark_reports/source_update_flow/freeze_batch.py <批次目录> <批次目录>/batch_manifest.json --original-documents <Word原件目录>
   python benchmark_reports/source_update_flow/flow_gate.py <批次目录>/batch_manifest.json --phase intake
   ```

   清单从**实际读取文件**生成，不从目录显示的汇总数字推算。新批次必须传 `--original-documents`，并保持原件可验证。来源或解析结果变动时重新建批，不能改旧清单继续发布。

## 2. 全量比对与逐项结论

按网站资料集 ID + 条目 ID 固定来源身份，再比较完整正向正文、同正文旧记录及其个人字段。每条网站记录写入 `source_registry.json`，结论至少分为：已有资源、已有基础词条、新增资源、新增基础词条、来源保留、无正文；正文冲突单独裁决，不用上游截断文本覆盖本地完整版。短 tag 和长正文分别进入基础词库与资源库；不同库中的同正文要核对关联，不重复制造资源。来源目录只用于来源展示和辅助定位，不能代替语义证据。

**新版完全一致优先规则：**确认网站发布先后、固定 release 和条目哈希后，如果新旧正向正文相同（含已验证的空格/下划线等规范等价写法），复用一个主 Tag 身份，以新版原文、来源版本及已验证图片作为主显示值；旧来源放入来源历史，旧正文副本和非目标字段保留。同一新版内若有多个来源使用同正文，各来源图片均下载并保留来源到本地文件的绑定，界面单预览选该批后出现的来源。不得用“正文相似”覆盖；正文不同、来源先后不明或图片未验证须逐项裁决。可复用的元数据合并函数见 [新版来源优先规则](newer_source_policy.py)。

Word 的每个解析条目必须在 `document_coverage_receipt.json` 有对应结论：网页精确覆盖、本地精确覆盖或人工裁决。`unresolved` 必须为 0；解析碎片不得作为独立提示词导入。来源保留规则先于新增、图片和分类处理，保留项计入覆盖审计但不被图片数量自动放行。

### 已有来源的细微修订核对（每次同步必做）

增量同步同时包含新增来源和已有来源修订。以最近一次实际验收的固定快照为基线，用 `dataset + entry_id` 对齐全部来源身份，分别列出新增、移除、已有修改和完全未变；不能仅检查新 ID、`isNew`、版本号或条目总数。

已有条目先比较完整原始 JSON 字段，保留字段缺失/null、值类型、字符大小写、空格、下划线、标点、权重及数组顺序差异。核对包括主 tags、负向提示词、角色分段、标题/说明/备注、参数、图片路径和修订标记、逐图提示词及图片与正文的绑定；未知新增字段也必须进入差异台账。规范等价判断只能在记录原始差异后用于裁决，不能提前抹平变化。

同时核对资料集目录/路径配置、数据集 JSON 中 `entries` 之外的字段（含 `tree` 及既有树节点）和外部 `dataUrl` 实际字节；目录 `codexes.json` 不能替代数据集自身字段的核对。在核对结束再次检查网站指针和外部数据源，防止同一轮混入不同版本。文件哈希与已验收快照完全一致时可复用既有条目核对结果；有变化的文件按全部旧身份比较，无需重做无关资料分类扫描。

每条已有修订必须记录旧值/新值或对应哈希、变化字段、对应本地 Tag/资源 ID、实际同步字段及保留原因。正文不同的修订须逐项检查，不能按相似度覆盖或另建重复 Tag。来源说明与个人备注分开处理，保留正式收藏、个人备注、使用记录和旧来源历史。仅 `isNew` 或上游显示状态变化也要记录，不能混称提示词内容更新。

交付报告分别给出“网站已有条目发生修订数”“已同步到本地数”“保留未同步数”“本轮无新修订数”。新 Tag 数、已有 Tag 新增来源数、已有来源正文修订数不可混用。没有新修订时记录核对完成与当前快照，不强行写库。

## 3. 分类与图片审核

以 tags 原文和完整正文的核心语义判定主类、父类、细分及计数。核对正向、负向、角色分段、标题与上下文；证据不足保留上位或未定，并写下具体理由。新增自动候选要全文复核。任何分类规则或父归属改动都须测量影响半径、复核命中全文、历史回放、精确声明差量，再与数据和投影一起暂存。不能以扫描器标记数代替人工结论；扫描范围之外不宣称语义全对。分类依据见 [分类标准](../分类标准.md)。

图片审核同时报告三个数字：可纳入且有首张本地预览的来源行、来源保留/无正文带图行、多图的额外张数。首图交付须逐项验证本地文件可读和绑定；已有词条碰巧有预览不等于新来源图片已安装，更不能覆盖个人预览选择。若本批承诺“每张图可在本地浏览”，清单 `review.image_scope` 设为 `all_images`，图片收据必须给出 `all_source_images_verified`，并完成界面多图验收；只交付单预览则设 `first_preview`，额外图片明确保留来源链接。

## 4. 隔离暂存与发布门

先生成隔离的资源数据、语义投影、基础词库、共享关联、引擎文件和图片计划。结构校验要证明无非声明删除、无同正文资源重复、原有收藏/备注/历史/个人资格不变，SQLite 完整，分类绑定和完整索引一致。再完成图片哈希与可解码检查、历史冻结回放、分类扫描裁决、查询合同和恢复演练。所有收据必须指向同一暂存数据哈希；`preflight.json` 绑定暂存文件、处置清单和验证收据的哈希。

逐项复核来源保留与分类后，把清单 `review.source_hold`、`review.classification` 改为 `true`，并声明图片交付范围。然后执行：

```powershell
python benchmark_reports/source_update_flow/flow_gate.py <批次目录>/batch_manifest.json --phase stage
```

门禁失败时停在暂存。发布脚本必须由该批次配置驱动，不可复用旧批次写死的 PID、计数或目录。发布前再次核对生产基线哈希、8188 唯一监听者的 PID/创建时间/命令、空队列和回滚备份；先装并校验增量图片，再受控停机、处理 Tag DB WAL、原子替换数据、投影和关联文件，重启后核对同一进程归属。异常时恢复整组备份和索引/DB，并写明 `rolled_back`，不能继续标记 `accepted`。

## 5. 在线验收与最终交付

发布后验证生产文件哈希、完整在线索引与暂存重建一致、每个资料集代表条目及边界样本、图片 HTTP、查询合同、空队列和工作台无降级。线上失败必须恢复或保持明确未验收状态。仅在发布收据 `accepted`、线上逐项及查询合同通过后执行：

```powershell
python benchmark_reports/source_update_flow/flow_gate.py <批次目录>/batch_manifest.json --phase delivery --current-pointer <本次查询的当前网页指针.json> --require-current
```

若网站当前指针变了，固定版本可以验收为**该版本已交付**，但“当前全站已交付”会被拒绝；先制作差量新批次。最终报告写清固定 release、Word 原件版本、实读及逐项处置条数、资源/基础词条增改、保留原因、首图和额外多图、分类未定项、历史/索引/线上结果、生产哈希、回滚目录和未覆盖范围。`EXECUTION_STATE.json` 用 `staged`、`preflight_passed`、`accepted` 或 `rolled_back` 的真实状态，不把暂存和旧版验收写成当前生产。
