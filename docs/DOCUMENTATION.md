# 自述与文档怎么维护

入口供人快速理解，技术说明供人和 AI 深读。每份信息保留一个权威位置，其余用相对链接指向它。

## 简短自述

目录 README 建议 20–50 行，按实际复杂度调整。写清下面四件事即可：

1. 这个目录做什么。
2. 最常用的文件各做什么，先读哪一个。
3. 维护入口、输入/输出和会改动哪里。
4. 到哪里看完整方法、示例、测试与更新记录。

先用中文短句说明用途，再用表格列并列文件。避免首页堆满旧批次数字、临时路径、长日志和未核实的“全部通过”；当前状态由工具与对应回执提供。

## 文件头注释

本仓自己维护的入口文件用 2–5 行说明“用途、输入/输出、实际写入范围”，必要时附详情文档路径。注释解释用途和边界，复杂参数、原理和样例链接到功能 MD。

第三方源码的原注释、许可证和归档原件保持其来源身份。运行源码的注释修改也须同步清单与对应技术说明，经过相关验收后才能部署。

JSON、SQL 和资料分片不插入非格式注释；使用目录导航、schema、示例或相邻的技术说明解释。`snapshot/` 的导航统一放在[快照目录说明](SNAPSHOT.md)，不随意增加未登记载荷。

## 人与 AI 的阅读顺序

```text
根 README → 项目地图/目录自述 → 功能技术 MD
                                ↓
                         catalog.json → 实现、测试、示例、证据
```

AI 先读 [AGENTS.md](../AGENTS.md)，再按[技术目录](technical/README.md)找实现。机器目录的字段分别表示功能说明、实现、测试、示例、证据与最具体维护范围；它不代替真实功能验收。

新增目录或主要入口时补相应短说明，维护 `catalog.json` 的入口和归属；功能改动同步对应技术 MD 的短更新，项目变动登记 [CHANGELOG](../CHANGELOG.md)。

提交前检查本次说明已进入暂存区，再执行技术目录与提交门禁。命令见[日常维护](MAINTENANCE.md)，完整例子见[示例目录](../examples/README.md)。
