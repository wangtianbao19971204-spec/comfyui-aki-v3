# 2026-10-11：修复 K2 擦线（擦除）从未生效

用户问"擦除为什么没生效"。查证后发现**三重问题**，逐个实测隔离：

## 三个原因

1. **`[05C7] 遮罩擦线合成` 的输出没有下游消费者。** 节点 `1147` 的输出只接到 `[05V7]` 预览；控制链实际取的是 `1191 [05B4] DepthAnything ← 1153 ← 1190 参考图`。也就是说擦除算完就丢掉了——这是最根本的一条，静音或遮罩文件都不是主因。
2. **`[05C2] 白色擦线遮罩输入`（节点 `1164`）被静音**（`mode=2`），其 `MASK` 输出不会送达合成节点。
3. **控件里的文件名是错的**：`widgets_values[0] = ComfyUI_temp_oflff_00001_.png`，这是 7/5 由 SaveImage/PreviewImage 写出的一张**普通 RGB 成图**（黑底 + 白色区域、无 alpha）。节点 `properties.image` 里仍保留着**最后一次遮罩编辑器保存**的产物 `clipspace/clipspace-painted-masked-1782566128506.png`（RGBA、586512 透明像素、bbox `(0,0,1024,1343)`）——真正能生效的那张。

最小 API 图单独验证擦除链本身是好的（输出 = 黑色 SolidMask 按遮罩贴到线稿上）：

| 遮罩文件 | 合成输出差异 |
|---|---|
| `clipspace-painted-masked-…png`（RGBA） | 变化 **20.17%** 像素、bbox `[0,0,767,919]` |
| `krea2-mask-opaque.png`（无 alpha） | 0 |
| `ComfyUI_temp_oflff_….png`（无 alpha） | 0 |

## 修复

`production_tools/fix_krea2_erase_mask.py`：把 `1164` 解除静音并把 `image` 指回编辑器保存的遮罩。
`production_tools/connect_krea2_erase_to_control.py`：把 `130160.input_01` 的来源由 `1191` 改为 `1147`（擦除后的线稿），使擦除真正进入控制图；与 Anima 分支把 `05C7` 交给 LLLite 的做法一致。

`130160` 因此成为：`input_01` = 擦除后的线稿（默认），`input_02` = VNCCS 姿势深度。深度来源选择器的原意（换掉参考图深度）保留。

## 验证（隔离实例）

- 结构：校验脚本更新为新的期望接线并通过（根节点 294、连线 390、无悬空连线、"擦除合成必须喂给开关一次"、"遮罩节点必须非静音"）。
- 同会话 A/B/C（固定种子与提示词，只改遮罩状态）：

| 对照 | 结果 |
|---|---|
| A（编辑器遮罩·激活）vs B（重复） | **逐像素相同** ⇒ 确定性正常 |
| A/B vs C（旧文件·静音，即修复前） | 平均差 **24.60**、变化 **104900** 像素 |

- 另一组对照显示 `[05V7] 擦线后线稿预览` 也随遮罩改变（mean 36.17 → 24.40），与上述结论一致。

## 踩过的坑（记录以免重犯）

- 早期"静音 + 换文件后控制图逐像素不变"的结论被**测试脚本自身干扰**：脚本在准备阶段会把整条 k2 分支解除静音，于是"静音"这一变量在那些运行里并不存在。真正暴露问题的是同会话、逐档只改一个变量的 A/B/C。
- `partial_execution_targets` 必须是**字符串**列表；传整数会被后端 400 拒绝（`node_validation`），而前端脚本若不读响应体就只会看到"提交失败"。
- 隔离实例重启时若端口仍被旧进程占用，脚本只重启前端不会换后端图；诊断图接线时应直接读运行实例里的工作流文件，而不是依赖页面缓存。

## 限制

- 擦除的视觉效果（擦成黑色区域后对成图的影响）只验证到控制图层面，未做画面级评估。
- 遮罩语义是 `mask = 1 - alpha`：**透明处才会被擦除**；预览 `[05V6]` 可直接确认范围。
- 未改动遮罩文件内容与用户的提示词、种子、底模、步数等参数。
