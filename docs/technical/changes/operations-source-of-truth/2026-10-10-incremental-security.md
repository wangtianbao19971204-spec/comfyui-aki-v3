# 日常上传复用已验证内容

日期：2026-10-10；最终验收：2026-10-11。

此前 pre-commit 已有暂存缓存，pre-push 每次仍重新执行所有历史对象的内容规则。主仓本轮有约 8.3 万个可达对象、7.75 GB 对象内容，少量源码修改也要重复做大量相同的模式匹配。Git 网络推送本身一直是增量传输，不需要重新 fork 或复制整个仓库。

## 改动

`security_guard.py --all-history --cache-history` 与 `--pre-push --cache-history` 复用本机成功检查过的干净对象内容结果；pre-push hook 默认启用。仍重新枚举所有可达历史、读取全部对象字节并核对 SHA-256，检查所有历史路径、refs、commit/tag 消息、gitlink、manifest 顺序和跨分片边界。新增对象执行完整规则，旧文件被删除不能消除其历史检测结果。

历史缓存与暂存缓存分别保存于 Git 管理目录，不含正文、首尾片段、凭证值或可读路径。规则／代码／Python／审核登记变化使缓存失效，单个对象或路径别名改变重新扫描该对象；复制到另一克隆或工作树的缓存因目录身份不同而失效。损坏、SHA 不符回退完整扫描；失败或扫描期间状态漂移不更新缓存。压缩载荷和审核例外每次重新检查。历史缓存上限为 64 MiB／40 万条，超过上限不会跳过扫描。

无缓存仍是 `run()` 与 CLI 默认值，release／bundle／CI 的调用保持不变。`--cache-staged` 不能用于历史模式，`--cache-history` 不能用于部分内容／仅名称／暂存模式。缓存只省重复内容匹配，不是绕过上传门禁，也不证明不存在所有形式的私密资料。

## 验证

专项测试比较增量和无缓存的检测结果，覆盖新提交、删除后的旧密钥、禁止路径改名、commit/tag/ref 名、分片重排、压缩与审核例外、规则／登记变更、缓存损坏／摘要错配、跨仓缓存、硬链接、历史容量、并发漂移与 push 根校验。173 项相关回归通过，hook 语法、工作树／暂存区技术目录检查通过。

本机相同 refs 的 82,588 个对象、7,750,769,463 字节对照，两次均通过；检测结果、对象／字节数、历史 refs、审核例外、压缩载荷和分片边界完全一致。首次内容检查 **859.9 秒**，复用缓存后 **31.9 秒**，本次约 **26.94 倍**。复用 82,458 个对象的规则结果；130 个不可缓存对象（约 24.86 MB）仍重新执行内容匹配。全部对象的字节仍重新读取并验证 SHA-256。

这是本机每种模式一次的观测值，初次历史扫描的一部分时间与暂存门禁并行，未清理操作系统磁盘缓存。摘要、范围和原始报告摘要见[验收收据](../../../receipts/incremental_security_20261011.json)。本机缓存只作为后续日常检查的性能数据；新 clone、规则升级或缓存损坏仍需建立新的完整基线。

## 对日常文件维护的影响

LoRA 权重留在仓外。按本次文件清单确认新权重的内容与来源，不因改名／归档运行 Git 全历史门禁，也不按文件名或修改时间认定重复；同内容无需再次覆盖。源码部署计划原本就用 SHA-256 筛出新增和变化文件，本次不改生产部署逻辑、在线资料或已有模型。

回滚只需还原维护脚本和 hook 的改动。缓存是可丢弃的本机性能数据；默认无缓存扫描仍可使用，不依赖额外数据库、模型或网络服务。
