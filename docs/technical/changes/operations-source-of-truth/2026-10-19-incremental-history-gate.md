# CI 的可移植增量历史门禁

日期：2026-10-19。

## 问题

每次小改动都要等同一道全历史凭证门禁。仓库现有 83,218 个受检对象 / 7,913,476,408 字节：本机冷扫 **1012 秒**，GitHub 免费 runner 上 **29 分 45 秒**，占一次 PR 检查的九成以上。

实测成本结构（同一台机、同一份 refs）：`rev-list --objects --all` 枚举 142,003 条约 **0.31 秒**，`cat-file --batch-check` 元数据 **0.30 秒**，`git fsck --connectivity-only` **0.68 秒**，重算 7.9 GB SHA-256 约 **41 秒**，而逐字节内容规则正则约 **9 分钟**。所以「少枚举」没有意义，「复用已核验对象的内容判决」才是有效方向；而机器的修改时间、提交时间都不能作为判据——它们可伪造，且每次 clone 都会被重置。

## 改动

- `security_guard.py --all-history --cache-file <文件> --incremental`：判据换成 Git 对象身份。同一 OID 就是同一份字节，缓存里已有干净判决的对象不再读取，新出现的对象照旧读取全部字节、重算 SHA-256 并跑全部规则。
- 每次仍完整执行：全部可达对象与历史路径别名枚举、ref 名／文件名规则、禁止路径、超限 blob、敏感路径登记；`.part` 与 `snapshot/manifest.json` 的真实字节读取与跨片边界比较；另跑 `git fsck --connectivity-only` 作为独立的对象图检查。
- 压缩载荷、审核例外、历史路径例外从不写入缓存，因此每次重扫。
- 可移植身份是仓库级：远端 URL、根提交集合、可选 `COMFYUI_SCAN_SALT`，再加工具码／缓存码／Python 版本／规则／审核登记指纹。任一项不符即整份作废并退回完整扫描；本机 `--cache-history` 仍绑定 Git 目录身份，行为完全不变。
- 写入条件不变：整次扫描零发现且 refs／规则稳定才原子写入。CLI 拒绝没有 `--cache-file` 的 `--incremental`，也拒绝与暂存、内容审计、本机历史缓存混用。

## 验证

本机同一份 refs 的对照：冷扫 1012.1 秒，增量热扫 **21.7 秒**（约 47 倍）。对象数、跨片边界（120）、审核例外（116）、压缩载荷（14）与无缓存扫描一致；热扫跳过 82,881 个对象的字节，仍实际读取 1,283,271,012 字节，即 `.part` 分片与 manifest。`test_history_scan_cache.py` 25 项全部通过，其中本轮新增 7 项覆盖冷／热、字节跳过计数、新提交拦截、分片重排、跨仓缓存拒绝、损坏回退、salt 失效与非法组合。

## 边界

缓存不是发布许可，`publication_evidence` 始终为 `false`。拿不到缓存、缓存损坏、规则或工具变化都会自动退回全量扫描；正式发布、bundle、每周定时任务与显式 `--all-history` 仍是无缓存全扫。本记录只覆盖本机同一 refs 的对照，CI 上的真实耗时与跨运行缓存命中须由合并后的推送运行确认，不能用本机数字推断。
