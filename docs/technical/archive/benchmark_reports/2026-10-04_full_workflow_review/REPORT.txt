二、真实总体架构：九条独立分支，不是九段流水线

主生产 A1/A29：
  主正向/负向 + 底模/编码器/VAE + LoRA
    → 可选兼容控制 → 基础采样/解码
    → 手 → 脚 → 区域标准或快速（二选一）→ 脸 → 眼
    → 可选 1.5× UltimateSDUpscale
    → 最终预览/保存 + 可选显存清理。

Krea2 主生产：
  文生图 / 输入图图生图 / 输入图遮罩修复
    → 对应 latent 和 denoise 路由 → 可选 Depth 控制
    → 主采样/解码 → 可选 1.5× USDU → 预览/保存。
  当前没有接入 A1/A29 的六个部位细化子图；不能说三个主模型分支拥有完全相同的细化能力。

04–09：单独加载图片的工具分支。当前不会自动接收主生产分支终稿。
08/09 不是主链中必跑的“第三、第四阶段”。想继续处理，要选取前一步输出，再切换并启用该工具。

当前正式活动分支为 a1。其他八支是整支静音；这不代表里面每个可选工具以后都会自动打开。
节点 mode=0 为有执行资格，mode=2 为静音，mode=4 为旁路。
最终是否计算还取决于父子图状态、所选输出目标、条件路由和缓存。

区域细化（非露骨技术层面）：
  使用专用 YOLO segm → SegmDetectorSEGS → 类别过滤 → DetailerForEachPipe。
  不使用上述 bbox+SAM 链。可切换动漫/半写实及 2D/写实检测权重。
  当前默认选择动漫/2D；两个布尔值是在选检测器版本，不是在分别启用/禁用两种区域处理。
  标准当前 16 steps / denoise .30；快速 12 steps / .26。guide_size 768、max_size 1280。
  检测模型的全部识别标签不等于当前标签过滤器实际处理范围。
  本轮仅检查结构、选择器、参数与导出，不进行此区域的图像生成或画质宣称。

是否额外底模/专修 LoRA：
  当前 A1/A29 部位子图没有额外扩散底模 Loader，也没有局部专用 LoRA Loader。
  它们接主线传入的模型、CLIP、VAE、条件；主线 LoRA 会随模型传入。
  “基础/修复 LoRA”栏只是全局 LoRA 分类，不是只作用于细化的专用修复管线。
  refiner_ratio 存在不等于接了 refiner；当前相关 refiner_basic_pipe_opt 没有连接。
  YOLO/SAM 是识别模型，OmniSR 是像素超分模型，都不能算成“额外精修底模”。
  04 指令编辑额外加载的编辑 LoRA 是另一回事，不要和部位修复混淆。

六、二放与交付放大

三条主生产线各有一个 USDU，均默认关闭、最终 upscale_by=1.5。
  A1 #1051：12 / CFG7 / res_multistep / beta / denoise .12。
  A29 #1112：12 / CFG3.5 / euler / sgm_uniform / .12。
  K2 #1192：4 / CFG1 / euler / simple / .03。
  三者 tile 1024×1024，tile padding 64，mask blur 16。
  A1/A29 仍是 Half Tile + Intersections，seam denoise .42。
  K2 当前已发布 Band Pass，seam denoise .03，宽度64、blur16、padding32。

当前 Anima 是“所有已开启的部位细化之后再二放”，并非二放后还有第二次脸眼细化。
这个顺序有合理性：先修局部，再统一交付尺度。代价是后续扩散二放仍可能改变已修好的细节。
不能据此直接宣布应反转顺序：先二放再修局部是另一方案，需要真实 A/B，不是现状错误的充分证据。
Anima 二放取 LoRA/AuraFlow 后、参考控制前的模型，保留 LoRA，不继续沿用主图 LLLite 控制；这不是丢掉 LoRA。

“二放”表示第二阶段处理，不等于 2×。
OmniSR 模型名含 4×，USDU 最终倍率却为 1.5×；08 的最终倍率为2×；09为4×。
建议在 UI 同时显示“处理方法 + 最终倍率/尺寸”，避免只用含糊的“原生二放/4x基础放大器”。

K2 上轮有限实测已接受，不能把 .03/.03 无条件推广给 Anima，更不能把 Anima .42 缝补直接回填 K2。
本轮没有修改任何二放参数。

八、UI 与交互完整评价

当前有四层入口：
  1. ComfyUI 原生画布、顶部运行/队列、工作流标签。
  2. UAP 分支和阶段导航。
  3. 常用控制台：日常提示词、模型/LoRA、开关、主参数。
  4. 统一工作台：工作区/资料库/模型/图库 + 任务选择 + 结果区；另有 LoRA Manager 和各选择器。

做得好的地方：
  - 分支“浏览”和“启用”分开；非活动分支编辑字段禁用，避免只是看一下就改运行路线。
  - 九分支隔离副本逐一切换并导出，活动计算分支数量始终为1。
  - 原节点跳转保留高级编辑入口；常用字段与原节点共用值，不是另一份独立配置。
  - 区域档位互斥、batch=1 约束、A29 LLLite 保护已存在。
  - 资料写入校验活动分支/节点/控件身份，旧目标失效拒写；存在预览/追加/替换/撤销的防误写设计。
  - 完整工作台按任务显示输入图与结果；选图/上传入口在任务区存在，不能说整套 UI 都没有上传入口。
  - 全局搜索有空查询恢复；本轮 Escape 清空后焦点留在搜索框。
  - 色彩、圆角、按钮、焦点与图标已基本统一，深色低饱和配色适合长时间看图。

真实观察到的不足：
  A. 日常控制台在1280×720下，从 y=267 才开始，面板可见高度约433px；顶部导航、标题、工具条占据大量高度。
     首屏主要是提示词顶部、模型上半段和部分工具，细化/主采样等常用项要继续滚动。
  B. 完整工作台桌面主内容可视高度约482px，内容约3301px；左侧资料导航与主体分别滚动。
     窄窗口760×900时没有整页横向溢出，但侧栏仍占约169px，主内容约3697px高。
     结果预览被排到长表单之后，初始几何位置约 y=3633，不能同时看结果调参数。
  C. 进入手部子图后父级UAP导航仍悬浮在上方，遮住部分模型和检测参数；需要手动收起导航或移动画布。
  D. 子图外层清楚，主画布跨区域连线仍密集；阶段跳转是镜头定位，不是隔离页面，因此邻接线条仍横穿目标组件。
  E. 常用控制台、完整工作台、悬浮按钮、原生左侧栏、快速组导航并存；“资料库/主题/分支”有重复入口。
  F. 大多按钮14px、辅助文本12px，桌面可用；大量同权重的描边卡片与说明文字压低了主要操作的层级。
  G. LoRA四栏顺序跨分支不一致：K2 的“汇合/追加”排在基础/修复之前，而 A1/A29 在后面。
  H. 抠图/纯超分仍显示通用提示词检查卡片；指令编辑仍沿用生图措辞，任务语义没有完全匹配。

两种运行入口尤其需要写清楚：
  完整工作台的“开始生图/开始反推”使用 taskPlan.queueNodeIds 定向提交。
  ComfyUI 顶部通用运行没有同样的任务输出限定，已开启的独立预览/反推等输出可能也被执行。
  常用控制台却提示“右上角运行”，用户可能认为两种按钮完全等价。
  上述结论来自 run_controls.js/task_activity.js 与图的输出结构；本轮不实际提交以证明费用或耗时。

视觉总体判断：有统一设计语言，不是杂乱无章；但“面板统一”早于“任务统一”。
比继续换颜色更有价值的是减少重复入口、明确当前任务、将结果固定在可见位置、把细化常用参数拉到近处。
本轮只核实实际深色主题和两个窗口尺寸，未穷尽浅色/多色主题、浏览器缩放、触屏和所有无障碍场景。
