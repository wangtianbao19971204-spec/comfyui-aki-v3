# 插件运行逻辑与交互方式分析（2026-09-30）

方法：先读代码，**再用真实浏览器测量**。凡是测量推翻了我读代码时的猜测，都以测量为准并注明。

## 一、结构

统一包 = 外壳 + 5 个被收编的插件（`modules/`）：

| 模块 | 作用 |
|---|---|
| `WeiLin-Comfyui-Tools-V52-FullPromptSelector` | 共享资料、Tag、六类选择器 |
| `comfyui-anima-tools` | Anima 标签/随机选择 |
| `ComfyUI-Danbooru-Gallery-V50-GalleryOnly` | 图库 + UAP 日常控制台 |
| `comfyui-lora-manager` | LoRA / 模型 / Embedding |
| `comfyui-custom-scripts` | 补全与工作流工具 |

工作台自己的 UI 层在 `web/`，约 25 个文件、合计约 300 KB。`__init__.py` 用 `modules.json`
清单按 `importlib` 逐个加载，**单模块失败会被回滚并记录，不影响其他模块** —— 这个降级设计是好的。

## 三、优化点：候选与结论

### 1. 轮询里的无谓 DOM 重建 ✅ **已修复并实测**

首版分析把它归因于"重建页脚目标下拉"，**实测后纠正了归因**：真正的大头是
**750 ms 同步循环里的编码器提示重建**（该元素由 P1-1 引入）。

**修复**：给编码器提示加内容签名短路——先算出待显示的文本，与上次相同就直接返回，
不再 `replaceChildren()` 重建三个子节点。

**实测对比（同样空闲 10 秒，两次独立运行结果一致）**：

| 场景 | 指标 | 修复前 | 修复后 |
|---|---|---|---|
| 工具页（待用列表） | 属性变更 | **8,069** | **51** |
| 工具页 | `desk-encoder-hint` 相关变更 | 78 | **0**（不再出现于前十） |
| 工具页 | long task | 0 | 0 |
| 工作区页 | 属性变更 | 8,425 | **409** |

即工具页的属性变更下降 **约 99%**，且没有引入回归（工作区页的 long task 数在修复前后都是 3–4 次，
来源见下）。

**改前/改后**：`uap_daily_controls.js` 由 `28715AF8…`（47500 字节）改为 `F9B3C645…`（48091 字节）。
备份：`backup_20260930_083850/js/uap_daily_controls.js`。
验证：`node --check` 通过；服务端 200 且与磁盘逐字节相同；编码器提示回归 8 项 + 模型选项 20 项
+ 六类选择器回归**全部通过**。

**仍未解决的部分（已定位，未动）**：工作区页空闲时仍有 3–4 次 long task（约 370–440 ms），
变更目标是 `danbooru-gallery-4-grid` / `-5-grid` / `-6-grid`（各 41 次）。
即**来源是随包引入的 Danbooru Gallery 模块自身**，不是工作台代码。
按"改最窄路径"的原则，我没有去改第三方 bundled 模块——那属于 Galley 的职责范围，
且没有证据表明它造成用户可见问题（我这次矩阵实跑与全部交互测试均未受影响）。

### 2. 打开工作台时的 DOM 规模

打开会新增约 2,634 个节点（关闭后不回收，但**5 个循环零增长**，属一次性开销而非泄漏）。
18k 基线里绝大部分是画布本身。**不建议为此改动**：102 ms 的打开耗时已经很快。

### 3. 我读代码时怀疑、但实测推翻的三处（如实记录）

我最初判断下面三处是"资源泄漏/定时器泄漏"，逐一核对后**全部是误判**：

| 我的猜测 | 实际情况 |
|---|---|
| 关闭后 750 ms 定时器仍在跑 | `close()` 里**有** `clearInterval(targetTimer)`；实测关闭后触发 **0 次** |
| `workspace.js` 的 `addEventListener('lora-manager:autocomplete-ready')` 只加不删 | 第 155 行的 `dispose()` **有** `removeEventListener`，且 `close()` 会调用它 |
| `run_controls.js` 的 `api.addEventListener` 是模块级、会越积越多 | 第 73 行 `dispose()` **有** `removeEventListener` |

因此**插件的生命周期管理其实是相当完整的**：定时器、事件监听、写入器、选择器都有对应的清理路径。
这一点值得肯定，也说明"再加一层清理"没有依据。

### 4. 代码风格：高密度压缩（值得知道，但**不建议动**）

`tag_manager.js` 是 79 KB / 1108 行（约 **73 字节/行**），远高于可读代码常见的 40–60。
读源码确认：这是**手写的压缩风格**（一行内多条语句、无空白），不是构建产物——仓库里没有构建脚本。

影响：可读性和可审查性下降，改一行容易碰坏相邻逻辑。但：

- 它有 6/6 的选择器回归覆盖；
- 项目规则明确"避免大范围重写""风格不符的改动会被拒"；
- 没有任何失败证据支持重构。

**结论：不动。** 只作为后续维护者需要知道的背景记录在此。

## 四、交互方式观察

结合前几轮的真实浏览器操作，交互上有两点是**实测到的摩擦**（不是猜测）：

1. **资料库跨来源搜索有 300 ms 防抖，但等待期间没有加载指示**（`workbench_shell.js:439`）。
   慢响应时用户无法区分"还在搜"和"没结果"。建议加一个轻量"搜索中…"状态。
2. **选定写入目标后没有任何确认反馈**。页脚只是把选项改成"将应用到：…"。
   这一点我在测试时确认过：目标选定是即时的，但没有视觉/文字确认，用户可能不确定是否生效。

这两点都属于小改动、低风险，但**需要你先认定它们是问题**——因为它们改变的是主观体验，
不是缺陷。我不想在没有你确认的情况下调整交互文案/状态。

## 五、结论

- **运行逻辑健康**：模块化加载 + 单模块失败隔离；打开 102 ms；关闭后定时器归零；5 循环零泄漏。
- **唯一有实测支撑的技术优化点**是第 1 条（空闲轮询里的无谓 DOM 重建 + 3 次 long task）。
- **两处交互摩擦**（搜索无进度反馈、选定目标无确认）需要你先判断是否值得改。
- 三处我怀疑的泄漏**全部不成立**，已撤回，避免基于错误前提去"修"出问题。
