# 唯一主仓与本地运行工作区

本项目只以本仓 `main` 的受审查提交为开发与维护来源。运行目录不是第二个开发仓；仓外档案也不是可继续提交的工作仓。上游更新先在主仓导入、评审和验证，再按范围部署，不在运行插件目录执行 `git pull` 或启动器的一键源码覆盖更新。

## 三者的关系

| 位置 | 权威内容 | 不能做什么 |
|---|---|---|
| `maintenance/comfyui/` | 本体、插件、工作流/子图、维护与训练工具源码、真实资料的受审查导出、结构契约、脱敏历史 | 不保存 API key、二进制数据库、权重、原图、私有 Git 原件 |
| 仓外本地资料根（本机 `G:\ComfyUI-local`） | 私密配置、机器引用清单、原始历史/回滚、隔离验收和交付包 | 不作为另一套日常源码；不能整目录上传 |
| 运行根（本机 `G:\ComfyUI-aki-v3`） | 主仓的部署文件，加上外部配置、依赖、模型、预览和最新运行态 | 不开发提交；不能用旧 SQL 快照覆盖当前在线数据库 |

模型、原图、环境和当前数据库仍可留在既有运行路径，作为明确登记的**仓外引用**。外置不等于必须搬动几百 GB 或让运行插件路径失效。小型私密配置可以另存到 `private-config/`；应用后续更新配置时，必须重新登记/备份，不能把旧外部副本视为自动同步。

本地实际环境 = 主 Git 的公开文件 + 明确引用的私密配置/大资源/运行数据。三个边界中，只有一个代码维护权威；可变运行数据则以应用最新数据为准，Git 中的导出是有时间戳的检查点。

“Git + 大文件/多图片/缓存 + 私密资料区”表达这个组合，但还必须包括匹配的 Python/CUDA/前端依赖环境和最新数据库。私密资料区不是第二个 Git，也不自动加密、同步或备份全部引用。2026-10-06 复核遍历全部运行子目录，识别 `.git` 文件、目录、链接和裸仓形态；遍历失败或主仓标记缺失不能判为唯一。目录链接不递归展开，其外部目标仍按资源/档案边界核对，详见 [复核收据](receipts/reassurance_20261006.json)。

## 仓外目录

```text
ComfyUI-local/
├─ private-config/   私密文件或本机鉴权环境，不公开
├─ manifests/        本机路径、角色、大小、哈希与外部依赖引用
├─ receipts/         清理、保护检查、组合验证与交付回执
├─ plans/            已审查的精确清理/组合计划
├─ archives/         原 Git、旧候选、旧验证树与回滚原件
├─ staging/          非权威的安全历史迁移中间物
├─ validation/       新版本的隔离克隆/还原，不用于开发
└─ releases/         已验证 bundle 与摘要，不是源码工作区
```

公开结构示例在 `governance/workspace-layout.example.json`，实际绝对路径与私密项清单只存本地。外部清单的角色、冲突规则和操作见 [外部状态组合](EXTERNAL_STATE.md)。`reference` 仅代表引用仍存在，不代表资源内容已经备份、哈希核验或完成冷启动验收。

## 日常修改

1. 进入本仓，核对最新提交、工作树和运行保护状态。
2. 源码修改 `snapshot/runtime/` 的唯一对应文件；资料/SQL 使用受审查导出，数据库迁移修改 `database/`。
3. 运行相关测试、`project.py seal`、快照校验及凭证门禁。`seal` 不表示部署。
4. 使用 `deploy-plan` 检查精确差异；额外审查工作流、配置和数据项。隔离验证后按范围部署并保留原件。
5. 用实际运行文件、服务身份和数据哈希验收。不要把离线还原或静态检查当成已启动/已生图。

历史 benchmark、训练数据、旧候选和下载媒体是仓外证据/数据。历史脚本可以用于审阅，不能直接从旧批次执行写死 PID、日期或路径的发布/回滚命令。需要继续开发时，把最小相关实现和测试明确导入主仓，保持来源记录。

## 清理与恢复

`scripts/archive_workspace.ps1` 只处理已指定的相对路径。先产生计划回执，再用其 `ReviewSha256` 执行；来源有变化、路径越界、活动锁、目标已存在或包含受保护根时拒绝。仅支持同盘可恢复移动，不调用删除命令。审核摘要用于绑定本次计划，不代表所有内容都做过相同等级的校验。

| 清单模式 | 实际核验内容 | 不能声称 |
|---|---|---|
| `Content`（默认） | 每个普通文件的路径、大小、SHA-256 | 已完成服务、数据库或冷启动验收 |
| `Metadata` | 普通文件的路径、大小、修改时间；清单本身另有摘要 | 文件内容 SHA-256 已核验、逐字节备份或抵抗同大小同时间的内容变化 |
| `Metadata` 加 `PreserveReparsePoints` | 另记录链接类型和目标字符串；不跟随 reparse point | 链接目标内容已复制、扫描、备份或验证完整 |

大历史树若含 junction/symlink，须先逐项审查链接清单和使用者，再明确选择保留模式。不得递归跟随链接进入外部依赖缓存，也不能把循环测试链接展开成实际目录。源根、目标根及其父路径仍不得用链接绕过路径边界。目录移动后若需要兼容旧回执、回滚路径或内部绝对链接，应按审核计划在**旧根位置**另建指向归档目标的 junction，并核对实际目标；归档脚本本身不自动创建该兼容入口。旧根 junction 只保留路径兼容，不赋予档案新的开发权威。

每项是否执行，以仓外 `receipts/consolidation-20261005/` 中对应的 review、apply journal 和后续核验为准。只有 review 是“已计划”；journal 部分完成时是“部分移动”；链接恢复也须有自己的验证记录。本文描述恢复规则，不宣称待归档目录已经移动。元数据模式的 `verified` 只表示元数据一致，不能升级解释为内容 SHA 验收。

回退时先确认无活动使用者，逐项核对原位置和归档位置。若原位置是兼容 junction，须确认其目标正是此次归档项，仅移除该链接本身，不递归删除或清理目标内容；随后在原位置未被新数据占用的前提下，将明确的归档项移回，并按原审核模式复核。不得覆盖后续文件、当前数据库或新的维护结果。

Git 退休前还须分别核对 tracked dirty、未跟踪维护文件和删除状态：搬走 `.git` 并不会自动备份工作树中的未提交文件。受审查源码应在主仓 manifest 中有对应身份，其余项须明确登记为仍保留的仓外原件；已有本地删除不从旧 HEAD 自动复活。原 Git、原始配置和回滚档案可能含历史凭证，属于私密 `original`，不可公开、不可继续开发提交，也不通过重新启用旧仓恢复日常开发。需要取回实现时，在隔离位置取出最小相关内容，经凭证审查后导入唯一主仓。

`workspace_guard.py` 记录并核对生产源码、资料、库主文件/WAL、私密配置、队列和服务身份。它只读，不停止服务、不清队列、不执行工作流。验收范围与本轮具体数字见 [工作区整理验收](ACCEPTANCE_WORKSPACE.md)。
